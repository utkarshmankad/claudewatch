# Token Watcher Product Hunt Delivery Plan

Phase wise roadmap prompts acceptance gates and launch measures

Planning date 10 October 2026 Planning assumption One primary developer and product owner with limited design and security support Target horizon Approximately 26 weeks with phase gates determining actual release timing
This plan turns the recommended Token Watcher build order into a sequence of implementation prompts. It begins with reliability because attribution, recommendations, synchronization, community intelligence, and growth reporting all depend on trustworthy timestamps and provider readings. The release should proceed only when the measured launch criteria are met or an explicit exception is recorded.

## Product direction

Token Watcher should become a privacy-first quota autopilot. It should explain where account-wide usage came from, recommend which provider to use next, maintain continuity across devices, detect provider changes, and help users decide whether their subscriptions are worth the cost. The product must label provider facts, local measurements, estimates, reconciled values, and unattributed activity separately.

## How to use the prompts

1. Run prompts in order within each phase. Begin the next phase only after the previous phase gate passes.
2. Give each prompt to the implementation agent as a complete request. The prompts include repository, branching, testing, pull request, and CI instructions.
3. Review design and privacy prompts before implementation prompts that depend on them. Do not combine these approval gates into one change.
4. Use develop as the integration branch. Promote one tested release candidate to main only in Prompt 6.5.
5. Record metric definitions before running experiments. Keep failed or unavailable measurements visible instead of replacing them with estimates.

## Launch success criteria

- Time to value Eligible users receive the first useful recommendation within two minutes of installation.
- Provider connection At least 50 percent of activated users connect two or more providers.
- Freshness Fewer than 1 percent of active sessions show unexplained stale data.
- Attribution At least 80 percent of eligible activity from supported local clients is attributed.
- Retention At least 25 percent of activated users remain active in week four.
- Growth At least 10 percent of weekly active users export or share a weekly report.
- Actionability At least 20 percent of quota-risk alerts result in a provider switch, explicit wait choice, or plan action.

## Program controls

### Decision cadence

Review delivery weekly and make a formal gate decision at the end of each phase. A gate review should include the measured outcome, evidence links, unresolved risks, security and privacy status, support impact, and the decision to proceed, extend the phase, reduce scope, or stop the initiative.

### Final launch decision

A Product Hunt date should be selected after the flagship workflow is reliable in production-like beta conditions. The launch candidate must detect current quotas, explain recent movement, recommend a useful next action, and produce a privacy-safe weekly summary. If that sequence cannot be demonstrated with live data in less than sixty seconds, the release needs another iteration rather than more launch promotion.

### Scope cuts if the schedule slips

Protect reliability, the Universal Usage Ledger, and Autopilot. Reduce breadth before reducing trust. The first cuts should be native mobile applications, additional browsers beyond Chrome and Edge, extra coding-tool collectors, public share links, advanced pricing scenarios, and broad Radar availability. Keep local-only operation, provenance labels, deletion, accessibility, security review, and rollback capability in scope.

### Definition of done for every prompt

- The change is scoped to the prompt and preserves unrelated work.
- User-visible behavior has acceptance tests and failure states.
- Provider integrations use sanitized fixtures and do not depend only on live accounts.
- Telemetry excludes prohibited data and includes a deletion path where applicable.
- Documentation, migration notes, security considerations, and rollback steps are current.
- Required CI, coverage, dependency, security, and smoke checks pass before merge.
- The pull request records measured results rather than stating that the feature works without evidence.

### Risks requiring explicit management

| Risk | Practical consequence | Required control |
| --- | --- | --- |
| Undocumented provider endpoints | Provider changes can make readings stale or wrong. | Fixtures, visible failures, kill switches, Radar, and rollback. |
| False attribution precision | Users may mistake estimates for billing records. | Provenance, confidence, unattributed values, and auditable reconciliation. |
| Extension permission distrust | Users may abandon installation or leave poor reviews. | Runtime permissions, plain explanations, local-only mode, and public data flow. |
| Solo-developer capacity | Parallel services can delay quality work. | Sequential gates, narrow platform support, managed services, and scope cuts. |
| Cloud security exposure | A breach could damage users and the product. | End-to-end encryption, minimal data, independent review, deletion tests, and staged rollout. |
| Vanity growth metrics | Shares or launch votes may hide weak retention. | Use activation, freshness, attribution, action rate, and week four retention. |
